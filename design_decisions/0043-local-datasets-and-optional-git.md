# ADR 0043: Select local datasets with optional Git synchronisation

- Status: Accepted
- Date: 2026-11-08
- Implementation: Implemented
- Extends: [ADR 0038](0038-open-source-tool-and-private-datasets.md)
- Revises: [ADR 0034](0034-knowledge-commit-and-push.md) for standalone dataset repositories

## Context

A public application must work without its developer's dataset or a GitHub account.
Most APIs already accept a dataset path, but CLI defaults selected `data/`, the
launcher changed the working directory, and Git sync required a mixed code/data
repository. These implicit locations make independent repositories difficult and
can select the wrong knowledge when a command is run from another directory.

## Decision

Keep local filesystem datasets as the only storage contract. Git is an optional
synchronisation mechanism over those same files. Clone with the installed Git
executable rather than a GitHub API, database adapter or new Python dependency.
HTTPS, SSH, file URLs and local Git repositories use the user's existing Git setup.
KNOT does not create hosted repositories, configure credentials or choose visibility.

Add `knot dataset init PATH`, `use PATH`, `clone URL [PATH]` and `show`. Setup selects
one dataset in user-level JSON configuration. Multiple datasets can be selected in
turn or addressed explicitly; no profile registry or persistent connection pool is
needed. `clone` can initialise an empty remote and chooses a managed user-data
location when no destination is supplied. It refuses existing destinations and
command transports, does not fetch submodules, and cleans only the directory it
reserved on failure. Configuration is updated after successful setup.

New datasets contain a version marker, a minimal organisation catalogue and graph
projections generated by the existing organisation API. They contain no invented
notes or manually constructed note registry. Existing note/graph datasets can be
selected without conversion. Unrelated nonempty folders are rejected; arbitrary
source-document ingestion remains a separate workflow.

Resolve paths at command boundaries: explicit argument, `KNOT_DATA_ROOT`, then
user configuration. A missing selection or invalid configuration fails; do not
silently fall back to a nearby `data/` folder. Explicit paths retain first-note
creation support. Core Python APIs continue to take explicit paths. Preserve the
caller's working directory in the launcher, and expose a package console entry
point. Viewer output defaults to the selected dataset. MCP uses the same selection
at startup without changing grants or authoring/review permissions.

Standalone Git sync uses the dataset repository root. Retain legacy `<git-root>/data`
support for existing private repositories. The first push of an empty clone can
create its initial commit and upstream, using the user's Git author configuration.
Only an explicit push command prompts for a commit; setup never commits or pushes.
Exclude drafts, exported views, local runtime files and locks, including staged
transient files. Pull remains clean-tree, fast-forward only, with no automatic
merge, stash or rebase. Failed pushes retain commits for retry.

## Alternatives and tradeoffs

A GitHub-specific storage backend would add authentication and remote-read behaviour
while still needing local state for offline work. Git already handles transport,
credentials and independent versioning. Supporting a plain folder first keeps it
optional and works with other Git hosts.

Configuration introduces user state, so precedence and error handling must be
consistent across entry points. Setup writes an absolute path outside the code
repository; moving a dataset requires selecting it again. No configuration change
moves source files or broadens MCP grants. JSON matches existing project tooling
and supports atomic writes without adding a TOML writer dependency.

Git stores source history, but it cannot safely resolve competing note registry
edits automatically. Divergence still needs explicit resolution through Git and
KNOT's existing provenance rules. A standalone repository must contain only data
intended for its remote: Git pushes all pending commits, not just the current note.

## Verification

Synthetic tests cover repeatable init, unchanged existing datasets, relative paths,
configuration precedence, missing/corrupt selection, all main command surfaces,
MCP's separate access gate, standard clone transports, default clone destinations,
failed and unrelated clones, and rejection of command/credential-bearing URLs.
Local bare repositories exercise empty-clone initial push, a second clone, note
retrieval, fast-forward refresh and transient exclusions. Existing sync regressions
retain divergence, staged-file, unusual-filename and failed-push retry coverage.
No real remote, user configuration or personal dataset is modified by these tests.

Actual hosted authentication remains an environment integration check. The commands
require installed Git for clone/sync; local note workflows do not. Existing datasets
are not relocated automatically by this implementation.

## Publication review follow-up: managed paths

The public-release review found that a recognised dataset could carry a graph
symlink through clone admission, redirecting later reads and generated writes.
Resolve an explicitly chosen root alias, but reject symlinks and parent traversal
in managed descendants. Share that rule in the storage module and enforce it at
read/write boundaries as well as setup and refresh; admission alone cannot protect
against links introduced later. Default exports and drafts are managed paths,
while explicitly supplied external export destinations remain supported.

Path checks add filesystem metadata work. The recursive admission/refresh check
does not read source bodies; ordinary operations validate the paths they use.
A rejected refresh retains the updated Git checkout for explicit repair. These
checks preserve the existing storage and provenance contracts without introducing
a second store or changing authoritative data. Synthetic regressions cover
directory/file links, dangling links, post-refresh changes and valid root aliases.
